- **Storage** (`lib/store.js`): orders go in Render Postgres when `DATABASE_URL` is set, otherwise in `data/orders.json` as before. Each order is one row, kept whole as JSON (`orders` table: `ref`, `created`, `data`), so new order fields need no database change.
- **Statuses**: new → quoted → paid → cut → dispatched (or cancelled). Prices are kept in pence: `quote` is the confirmed price, `totals` is the configurator's estimate.
- **Payments** (`lib/payments.js`): Stripe Checkout (stripe-node 23). Which payment methods appear (card, Apple Pay, Google Pay, PayPal…) is set in the Stripe dashboard, not in code, as Stripe recommends.
  1. The customer sends a request. It's saved as *new* with a secret `payToken`.
  2. On `/admin`, Tim checks it, edits the price if needed and clicks **Confirm price**. The order becomes *quoted* and the page shows the payment link `/pay/<ref>?t=<token>` with a Copy button.
  3. Tim emails the link himself (there's no automatic email yet). The customer sees the order and the price and clicks Pay. Each click makes a fresh 2-hour Checkout Session, so the link never expires.
  4. The webhook `POST /api/stripe/webhook` (signature checked) marks the order *paid*. The thank-you page `/pay/<ref>/done` also checks with Stripe, in case the webhook is slow. A payment is recorded only once.
  5. **Mark paid (not Stripe)** on `/admin` records a bank transfer or cash payment.
- **Admin safety**: the buttons only work from the admin page itself (an Origin check), and the Spec download leaves out the pay token.
- **Tests**: `npm test` (`scripts/test.js`) covers the whole flow, including emails, refunds and the admin pages, with a stand-in for Stripe's servers and Stripe's real signature check. `TEST_DATABASE_URL=postgres://… npm test` runs the same tests against Postgres. Both pass.
- **`render.yaml`** now declares the `pivot-orders` database (basic-256mb, about £6 a month, Frankfurt, no outside access), plus `DATABASE_URL`, `SITE_URL`, `STRIPE_SECRET_KEY` and `STRIPE_WEBHOOK_SECRET`. The Stripe values are entered in Render, never in the repo.

## Admin workflow (rebuilt 20 Nov 2026)
- **No admin button emails a customer by itself.** Confirm price, Mark paid, Mark dispatched and Stripe refunds set `pendingEmail` (paylink, paid, dispatched or refunded) and show a red **Action required** flag, plus a **Needs action** list at the top of /admin. Confirm price, Mark paid and Mark dispatched then open `/admin/orders/<ref>/email?kind=…`. There Tim edits the subject and message, presses **Update preview** (a sandboxed iframe shows the exact email), then **Send email**, **Not now** (the flag stays) or **No email needed** (clears the flag). There's also **Email customer…** for a free-form message any time. Each send uses a nonce idempotency key, so a double click doesn't send twice.
- The automatic emails, all triggered by the customer, are: request received (to customer and Tim) and paid by card (to customer and Tim).
- **Refund tracking:** the Stripe `charge.refunded` webhook finds the order by payment intent (`store.findByPayment`) and records `refund.amount`. A full refund sets the status to `refunded`; a part refund keeps the status and notes the amount. Either way it flags a refund email. **Tim must add the `charge.refunded` event to the live webhook destination in Stripe.**
- **Delete:** `/admin/orders/<ref>/delete`. Unpaid orders need one click; paid ones need the reference typed, with a warning about keeping sales records for 6 years.
- **New order (Tim creates one):** the **+ New order** button opens `/configurator?admin`, which uses a separate saved door list, shows a yellow bar and posts to `/admin/orders` (basic auth plus a same-site check). The order is created with `source: "admin"` and no emails; then Tim continues with Confirm price. A built-in **How this page works** guide on /admin covers all the workflows.
- Archived = cancelled, refunded, or expired price, unless the order still needs action.

## Address capture (20 Nov 2026)
- The order form has a **Find your delivery address** search box (Ideal Postcodes, chosen by Tim; pay as you go, about 3–4p per address picked, and suggestions are free). It fills Address line 1, line 2, Town and Postcode, which customers can also type themselves.

## Hinge-hole charge and discount codes (built 27 Nov 2026, merged to `main` and live the same day)
Tim asked for both. Decisions made while building (Tim can change any of them):
- **Hinge holes**: /admin/pricing → *Hinge holes*: **No charge** (the default) or **Charge per door** with an amount (£0.01–£100). Saved inside the `pricing` setting as `hinges: { charge, perDoor }` (engine `PRICING.hinges`, `hingeCharge()`), so it's on `/api/pricing`. Charged once per door that has hinge holes, whatever the number of hinges; each door of an arched pair counts. It's added to the door price (so it counts towards free delivery and is discounted by codes). The Shop shows "Hinge holes add £X per door" under the hinge choice and "Includes £X for hinge holes" in the basket. Saving or resetting the band prices keeps the hinge setting. Orders store `totals.hinges`.
- **Discount codes** (`lib/discounts.js`, `discounts` setting, page **/admin/discounts**, linked from /admin and /admin/pricing): percentage (up to 90%) or fixed £ off the **doors only, never delivery**; free delivery is still judged on the doors before the discount. Optional minimum spend, last day, and use limit; switch off/on; delete. A use is counted when an order with the code is **paid** (Stripe or Mark paid), so abandoned checkouts don't use one up. Customers type the code in the basket ("Have a discount code?"), checked by `GET /api/discount?code=` (20 tries per visitor per 10 min, no private details returned) and checked again in `createOrder`: an invalid, expired, used-up or under-minimum code is refused with a message, not silently dropped. Works in both payment modes and in Tim's New order. Orders store `totals.discount: { code, kind, value, minSpend, amount }` and keep it if the code is later deleted. Shown on /admin (under the estimate), the pay page, all emails with the door list, and the Stripe description. In Quote first the estimate already has the discount off; Tim can still change the price.
- **Master switch** (Tim asked, 27 Nov 2026): /admin/discounts → *Discount codes on the website*, **Off** (default) or On (`discountsOn` setting). Off: no code box in the basket (`codes: false` on `/api/pricing`), `/api/discount` and `createOrder` refuse every code. Orders that already have a discount keep it. The /admin bar shows "Discount codes (off)" while it's off.
- Not done (ideas): one use per customer, codes limited to certain designs, codes that give free delivery.
- Tested in `npm test` and in a browser (desktop and phone basket).
